# Implementation Plan: Optimization Task Queue

**Branch**: `028-dss-optimization-split` | **Date**: 2026-04-14 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/029-optimization-task-queue/spec.md`

## Summary

Replace the fire-and-forget `Task.Factory.StartNew()` execution model in optimization and validation handlers with a singleton `Channel<ComputeTask>`-based task queue consumed by a `BackgroundService`. This ensures one compute-heavy task runs at a time, enables per-DSS trial cache reuse between optimization and validation phases, and provides a transparent queue UI with cancel/purge controls.

## Technical Context

**Language/Version**: C# 14 / .NET 10
**Primary Dependencies**: ASP.NET Core (minimal APIs), System.Threading.Channels, Microsoft.Extensions.Hosting (BackgroundService), System.Threading (CancellationTokenSource, Interlocked), existing AlgoTradeForge Application/Domain/Infrastructure layers
**Storage**: SQLite via SqliteRunRepository (existing) — no new tables; in-memory Channel\<T\> for ephemeral queue
**Testing**: xUnit + NSubstitute (existing)
**Target Platform**: Windows (dev), Linux (deploy)
**Project Type**: Web application (ASP.NET Core backend + Next.js frontend)
**Performance Goals**: Single compute task at a time; queue operations (enqueue, cancel, purge) < 1ms; status polling response < 50ms
**Constraints**: No new NuGet packages. Reuse existing patterns (Channel\<T\>, BackgroundService, RunProgressCache).
**Scale/Scope**: Single-node deployment; queue depth limited by available memory for task descriptors (lightweight)

## Implementation Phases

### Phase 1: Core Queue Infrastructure (P1 — US1)

**Goal**: Replace fire-and-forget with sequential queue processing.

1. **Create `ComputeTask.cs`** — record type, enums (ComputeTaskType, ComputeTaskStatus)
2. **Create `ComputeTaskQueue.cs`** — Channel wrapper with:
   - `Channel<ComputeTask>.CreateUnbounded(new UnboundedChannelOptions { SingleReader = true })`
   - `ConcurrentDictionary<Guid, ComputeTask>` for task lookup
   - Enqueue, TryCancelTask, PurgePending, GetSnapshot, RemoveCompleted methods
3. **Create `OptimizationTaskExecutor.cs`** — Extract from `RunGroupOptimizationCommandHandler`:
   - `RunSingleDssBruteForceAsync()` logic (data loading + parallel evaluation)
   - Accept pre-resolved axes, return `BoundedTrialQueue` + metrics
   - Accept `maxParallelism` parameter
4. **Create `ValidationTaskExecutor.cs`** — Extract from `RunGroupValidationCommandHandler`:
   - `RunSingleValidationAsync()` logic
   - Accept optional `IReadOnlyList<BacktestRunRecord>` for cached trials (skips DB load)
   - Falls back to DB load when cache is null (standalone validation)
5. **Create `ComputeQueueConsumer.cs`** — BackgroundService:
   - `await foreach (var task in queue.Channel.Reader.ReadAllAsync(stoppingToken))`
   - Skip cancelled tasks
   - Call appropriate executor
   - Manage per-DSS trial cache handoff
   - Fire-and-forget DB persistence (Task.Run) between optimization and validation
   - Register/deregister cancellation tokens
6. **Refactor handlers** — Replace `Task.Factory.StartNew()` with `queue.Enqueue()`:
   - `RunGroupOptimizationCommandHandler`: keep prepare logic, enqueue N×2 tasks (opt+val per DSS)
   - `RunGroupValidationCommandHandler`: keep prepare logic, enqueue N validation tasks
   - `RunOptimizationCommandHandler`: delegate to group handler (group of 1 DSS)
   - `RunValidationCommandHandler`: delegate to group handler (group of 1 DSS)
   - `RunGeneticOptimizationCommandHandler`: enqueue 1 opt task (+ optional val task)
7. **Register services** in `DependencyInjection.cs` and `Program.cs`

### Phase 2: Queue Management API & Frontend (P2 — US2, US3)

**Goal**: Expose queue state and controls to the UI.

1. **Create `TaskQueueEndpoints.cs`**:
   - `GET /api/queue` → snapshot with progress from `RunProgressCache`
   - `POST /api/queue/{taskId}/cancel` → cancel + cascade
   - `POST /api/queue/purge` → purge pending
2. **Create `TaskQueueContracts.cs`** — response DTOs matching contracts/queue-api.md
3. **Modify `RunOptimizationRequest.cs`** — add `Validate`, `ThresholdProfileName`, `MaxThreads`
4. **Create `frontend/types/task-queue.ts`** — TypeScript types
5. **Create `frontend/hooks/use-task-queue.ts`** — polling hook (2s interval, stop when empty)
6. **Create `frontend/components/features/dashboard/task-queue-panel.tsx`**:
   - Show pending + in-progress tasks with status badges
   - Progress display (combinations for opt, stages for val)
   - Cancel button per task
   - Purge pending button
7. **Modify `run-new-panel.tsx`** — add validate checkbox, threshold profile dropdown, max threads input

### Phase 3: Max Threads & Polish (P3 — US4)

**Goal**: Wire max threads parameter end-to-end and handle edge cases.

1. **Max threads backend** — clamp `0 → Environment.ProcessorCount`, cap at CPU count in executor
2. **Max threads frontend** — input field with 0 default, max = CPU count (from API or hardcoded)
3. **Edge cases**:
   - Zero passing trials → validation completes immediately with empty result
   - Application restart → `ComputeQueueConsumer` logs stale in-progress tasks on startup
   - Genetic single-DSS → enqueue 1 opt + optional 1 val
4. **Tests**:
   - `ComputeTaskQueueTests` — enqueue, cancel, purge, cascade, snapshot
   - `OptimizationTaskExecutorTests` — verify execution uses correct parallelism
   - `ValidationTaskExecutorTests` — verify cache reuse vs DB fallback

## Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| `Channel<T>` over external broker | Single-node, ephemeral, already used in codebase (LiveOrderContext) |
| BackgroundService consumer | Lifecycle managed by ASP.NET Core host; graceful shutdown |
| Extract executors from handlers | Handlers keep prepare+enqueue; executors are testable units |
| Data loading in executor (not handler) | Avoids holding market data in memory while tasks wait in queue |
| Fire-and-forget DB persistence | I/O doesn't compete for CPU; validation reads from cache, not DB |
| No new DB tables | Queue state is ephemeral; existing tables handle persistence |
| 2s polling (not SSE/WebSocket) | Matches existing patterns; simpler; sufficient for queue updates |
